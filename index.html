The framing for the whole talk: the most powerful dev tools, used by a dummy, for dummies. I’m a designer, not a developer. These tools are built for engineers, and the trick is that I don’t operate them: I tell Claude Code what I want and it does the work. This talk covers which tools, how they connect, and how I ask.

Claude Code

Build

  • You describe the outcome. It handles the code, git and GitHub.

  • Shows a plan, a diff and a live preview, so you review before anything ships.

read this figma frame, plan the build, implement it in this project, and show it in the preview

The desktop app, not the chat site. Walk the window: sessions on the left, the conversation, the live preview. Connectors are how it reaches Figma and the other services. Each session runs in its own git worktree.

Folders on your computer.

Plus its own saved context.

Claude Code04 / 22

Your folder

Project folder

Pick a folder or repo when you start a session. Claude reads, edits and runs commands there.

Worktrees

For Git projects, each session can work in its own copy under .claude/worktrees, so parallel tasks don’t collide.

Terminal

The built-in terminal opens in the same folder, with the same environment as Claude.

What it remembers

Session history

Each session has its own history, saved on your computer. A new session starts fresh.

CLAUDE.md

A file in the project with instructions you write. Claude reads it at the start of every session.

Auto memory

Notes Claude writes itself from your corrections and preferences, carried into later sessions.

What that looks like on disk

my-project/            the folder I pick
├─ CLAUDE.md           instructions I write
├─ .claude/
│  ├─ worktrees/       one copy per parallel session
│  └─ settings, skills, rules
└─ …your files
~/.claude/             global settings, skills, rules

Every Code session is tied to a project folder or repo on my computer. Claude reads, edits and runs commands there, and the built-in terminal opens in the same place. For Git projects each session can work in its own worktree under .claude/worktrees so parallel tasks don’t collide. Memory: each session has its own history saved locally and a new one starts fresh. What carries over is CLAUDE.md, instructions I write, and auto memory, notes Claude writes itself from my corrections. Settings, skills and rules live in the project’s .claude folder, with global ones in ~/.claude.

Claude Code: setup and use.

Install it. Open a folder. Go.

Claude Code05 / 22

Use it when

Any build or edit task: reading a design, changing code, running the app.

Day to day

Describe outcomes, not commands. Claude handles the files, git and tooling. Add services any time from + → Connectors.

Access it uses

Your project folder, plus whatever the permission mode and connectors allow.

How to set it up

Install the desktop app, open the Code tab, choose the folder. For Git projects pick the worktree option so each task is isolated; Claude manages the branch. Pick a permission mode, then describe what you want and review the preview and the diff. No terminal needed. Claude Code needs a paid plan.

A new worktree is a fresh checkout, so gitignored files like .env don’t come along. Ask Claude to list them in .worktreeinclude (worktrees docs).

Permissions.

How much Claude asks first.

Claude Code07 / 22

ModeWhat it does
ManualAsks before each edit and command.
Accept editsAuto-accepts file edits and common file commands like mkdir and mv. Still asks before other terminal commands.
PlanReads and plans. No edits until you approve the plan.
Bypass permissionsRuns without permission prompts. Anthropic’s docs recommend isolated environments. Safety checks still prompt on external sites.

Connections act with your account’s access. Each service page lists what that covers.

Press the white box to mark the two modes on the table.

Two layers. Connectors act with your account’s access, so scope them: Supabase can be limited to one project or read-only, and Tool access in the Connectors menu controls which tools Claude can use. Then the permission mode. Manual asks before each action. Accept edits auto-approves file edits and common file commands but still asks before other terminal commands. Plan blocks edits until you approve a plan. Auto runs everything with background safety checks. Bypass permissions runs without prompts, and the docs recommend it for isolated environments; safety checks still prompt on external sites.

How I run it: Accept edits or Bypass permissions on stable projects. Commits and worktrees make edits easy to revert.

Connect once. Work from links.

Figma10 / 22

Use it when

You have a frame or design system to build from.

Day to day

Paste a frame link, ask for the build, compare it with the design, and go again in small steps. Claude reads your styles and variables too.

Access it uses

How GitHub works.

Four terms. Claude handles all of them.

GitHub13 / 22

Branch

A parallel line of work in the same repository.

Enables: trying a layout variant without touching the version that is live.

Worktree

A separate checkout of the repo, on its own branch, in its own folder.

Enables: parallel Claude sessions that can’t overwrite each other’s files.

Pull request

A proposal to merge one branch into another, shown as a diff.

Enables: review, comments and automated checks before anything lands.

Merge

Folding one branch’s changes back into another, usually main.

Enables: approved work becoming the shared version, ready for Vercel to deploy.

Claude runs all of this. You just describe the change.

The terms, for recognition only. Claude does all of it. Branch: a parallel line of work. Worktree: that branch checked out in its own folder, which is how Claude Code runs several sessions without collisions. Pull request: a proposal to merge a branch, shown as a diff with comments and checks. Merge: folding the branch back into main. With auto-merge on in the repo, Claude can merge once checks pass.

GitHub: setup and use.

Connect once. No manual syncing.

GitHub14 / 22

Use it when

Any project you want versioned, shared or reviewed. Start from the first session.

Day to day

Claude makes the commits, branches and PRs, watches the checks, and can merge when they pass if the repo allows it. You review the preview and say what to change.

Access it uses

Your repo access via the connector and gh: reads and writes code, branches and PRs.

How to set it up

Connect GitHub once from + → Connectors, then say take care of GitHub for me. Claude creates the repo, makes the first commit and handles branches, PRs and merges from then on. No manual syncing: nothing to copy, upload or push by hand. PR creation and CI watching also need the GitHub CLI (gh) signed in; Desktop prompts you the first time.

Deploy

Vercel15 / 22

  • Builds and hosts every branch at its own URL.
  • Reviewers test the real build on real devices, with no setup.
  • Claude deploys it and sends you the link.

Example prompt

deploy this branch to vercel and give me the preview url

What it can do

  • Deploy
  • Preview URLs
  • Hosting
  • Domains
  • Environment variables
  • Rollbacks

Every branch builds at its own URL, so reviewers test the real thing on real devices. Merging to main promotes the build to production.

Link: vercel.com

Vercel: setup and use.

Import the repo. Get previews.

Vercel16 / 22

Use it when

You want a shareable URL for review, or a host for the front end.

Day to day

Open the preview URL on a phone, send it for comments, and Claude ships it when it looks right. If a deploy fails, ask Claude to check the build output.

Access it uses

Your Vercel team access: deploys, and edits project settings and variables.

How to set it up

Ask Claude to put it on Vercel and send a preview link. It picks the route, either the CLI or importing the GitHub repo, adds environment variables and fixes build errors. Keep keys in environment variables, never in code, prompts or screenshots.

Supabase17 / 22

  • A hosted Postgres database, browsable and editable as a table.
  • Sign-in and user management that Claude sets up for you.
  • Real data to design against, including empty, loading and error states.

Example prompt

add sign-in and a favorites table to this prototype using supabase

What it can do

  • Database
  • Sign-in
  • File storage
  • Auto-generated APIs
  • Realtime
  • Edge functions

Hosted Postgres with a table editor, plus sign-in and user management. Real rows to design against, including empty, loading and error states.

Link: supabase.com

Supabase: setup and use.

Connect it. Keep keys in .env.

Supabase18 / 22

Use it when

The prototype needs real data, sign-in or file storage.

Day to day

Describe the data, let Claude write the migration, then open the table editor to see the rows. Use real data to design empty, loading and error states.

Access it uses

Your project access: schema, data, SQL and migrations. Can be limited to one project or read-only.

How to set it up

Create the project, add the connector, then describe the data and sign-in you want. Claude designs the tables, runs the migrations and puts the URL and publishable key in .env. The publishable key is safe in the app because row-level security limits it; the secret key bypasses that and stays on the server. An API is how one program asks another for data or an action, and a key identifies the caller and sets what it may do.

Railway

Hosting and scheduled tasks

Railway19 / 22

  • Runs services that have to stay up: APIs, workers, databases.
  • Scheduled tasks, like a nightly data refresh, that Claude sets up and deploys.
  • Logs and metrics show what happened when a run fails.

Example prompt

set this up as a scheduled task that runs every morning and deploy it to railway

What it can do

  • Run services
  • Scheduled tasks
  • Databases
  • Variables
  • Logs and metrics
  • Deploy from GitHub

For things that have to keep running: services, workers and scheduled tasks, meaning work that runs on its own at set times, like a morning data refresh. Logs and metrics show what happened when a run fails.

Link: railway.com

Railway: setup and use.

Deploy from the repo. Schedule it.

Railway20 / 22

Use it when

Something has to stay running or run on a schedule: an API, a worker, a nightly refresh.

Day to day

Ask Claude to write the task, set the schedule and read the logs when a run fails. Claude handles the config.

Access it uses

Your project access: deploys, variables and logs.

How to set it up

Ask Claude to run it on a schedule and host it on Railway. It creates the project from the repo, adds variables and sets the start command or cron schedule. A scheduled task is work that runs on its own at set times, like a morning data refresh. Check the logs after the first run.
